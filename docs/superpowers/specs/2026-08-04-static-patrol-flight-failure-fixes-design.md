# 固定巡逻真实飞行失败修复设计

## 背景

2026-08-04 的首次六机真实仿真表明，静态几何测试通过并不等于实际飞行安全。该次运行的自动化 smoke 通过，但完整飞行验收失败：

- 4 号机沿 `y=12` 的巡逻线撞击 `house_1_146_clone`；
- 5 号机在任务管理器仍为 `IDLE` 时抢先进入人物跟踪，`PAUSE` 被忽略，之后一直没有完成第一个进入航点；
- 0 号机在接触采集开始前发生事故，后续坠地并产生异常全局高度；
- rosbag 中 0、4 号机的异常最高高度分别约为 490.143 米和 489.329 米，5 号机最高仅约 2.277 米；
- 起飞门控后的最小机间距离为 2.384 米。

本轮修复只处理证据已经闭合的两个根因：遗漏静态障碍和任务/跟踪启动竞态。0 号机的首次事故原因仍未确认，不在没有证据的情况下猜测修复。

## 约束

- 只修改队伍自己的 ROS 包、任务 JSON、测试和文档。
- 不修改 PX4、XTDrone、Gazebo、EGO-Planner-Swarm 或官方无人机模型。
- 允许按教程兼容模式调整任务航点、Launch 参数和队伍节点之间的话题接口。
- 无人机模型本身保持原版；本轮不涉及传感器安装位置。
- 首次失败证据必须保留在交接文档中，后续成功复验不能覆盖或省略失败记录。

## 方案

### 1. 补齐静态障碍合同

几何测试中的 `STATIC_OBSTACLES` 增加比赛世界内的：

- `house_1_146`；
- `house_1_146_clone`。

边界来自官方 `robocup.world` 中的模型位姿、`house_1.dae` 碰撞网格和 `1.5` 倍模型缩放。测试仍使用现有 2 米水平余量，并覆盖完整进入路线、巡逻路线和闭环末段。

先加入回归测试，使当前 4 号机路线因穿越 `house_1_146_clone` 而失败，再调整任务路线使测试恢复通过。不能通过缩小房屋边界或余量使旧路线通过。

### 2. 调整 4 号机静态责任区

4 号机仍负责北中区域，但其一次性进入路线先绕到房屋北侧，再进入房屋东侧的巡逻矩形。路线确定为：

- 进入点：`(0, 32, 3.5)`、`(25, 32, 3.5)`；
- 巡逻点：`(25, 12, 3.5)`、`(68, 12, 3.5)`、`(68, 41, 3.5)`、`(25, 41, 3.5)`。

这条路线保留北中区域的二维覆盖范围，同时让最靠近房屋的竖直边与碰撞网格保持额外余量。新增障碍测试和跨机 5 米中心线净空测试必须以这组确定坐标为输入。

### 3. 增加任务激活握手

单独依赖 `/swarm/takeoff_complete` 不能保证任务管理器已经离开 `IDLE`。每个 `MissionManager` 增加一个车辆级、锁存的布尔状态话题：

```text
/typhoon_h480_N/mission/active
```

状态合同：

- 节点初始化后发布 `false`；
- 任务管理器完成位姿等待和启动倒计时、进入 `ENTERING` 或 `PATROLLING` 时发布 `true`；
- `PAUSED`、`RESUMING` 仍属于已激活任务，保持 `true`；
- 进程退出由 ROS 连接状态处理，不伪造新的完成状态。

跟踪节点必须同时满足以下两个条件才允许请求人物目标或切换外部控制：

```text
/swarm/takeoff_complete == true
车辆对应的 /mission/active == true
```

任一门控关闭时，跟踪状态机保持或恢复 `IDLE`，释放已锁定目标，不发送 `PAUSE`。这样可以消除 5 号机所遇到的启动先后竞态，而不依赖固定延迟或 ROS 回调调度顺序。

## 数据流

```text
起飞节点 --/swarm/takeoff_complete----------+
                                            +--> 跟踪节点 --> PAUSE/RESUME
任务管理器 --/vehicle/mission/active--------+

任务 JSON --> 任务管理器 --> 航点目标 --> navigator --> MUX
人物检测 -------------------------------------> 跟踪节点 --> MUX external
MUX --> safety_filter --> XTDrone 最终速度话题
```

任务管理器仍是航点进度的唯一所有者；跟踪节点只在两个门控都打开后临时申请控制。PX4、XTDrone 和 Gazebo 不参与新增握手。

## 异常处理

- 只收到起飞完成、未收到任务激活：禁止跟踪，继续等待。
- 只收到任务激活、起飞未完成：禁止跟踪，继续等待。
- 已跟踪时任一门控变为 `false`：释放目标、清空跟踪状态并停止外部跟踪输出。
- 任务激活话题超时不额外推断为 `true`；锁存消息用于处理晚启动订阅者。
- 本轮不把坠落后的坐标发散误写成“正常超高”，但飞行验收仍按最高 `global_pose.z` 原样判失败。

## 测试

### 自动化测试

1. 几何回归测试先证明旧 4 号机路线与新增房屋碰撞，再验证新路线清障。
2. 保持六机任务高度 3.5 米、最终上限 4.0 米、跨机中心线净空至少 5 米。
3. 任务管理器测试验证 `/mission/active` 在启动前为假、进入活动阶段后为真。
4. 跟踪测试覆盖四种组合：两个门控均假、仅起飞为真、仅任务为真、两者均真；只有最后一种允许请求目标和发送暂停。
5. 运行任务管理器、tracking、safety_filter 相关测试及完整 competition-clean verifier。

### 真实六机复验

复验采集必须在起飞门控打开前启动，避免再次漏掉早期事故。必须记录：

- 六机完整进入阶段和至少一轮四航点闭环；
- 每架最高高度及门控打开后的最高高度；
- 全程和任务阶段最小机间距离；
- 完整 Gazebo 接触双方；
- 进入阶段和巡逻阶段的自然跟踪打断证据；
- 0 号机是否再次发生早期事故；
- 正常停止退出码、残留进程和 XTDrone 工作树状态。

任何无人机与无人机、静态建筑接触，持续异常高度、跨区巡逻、重复进入路线或无法完成闭环，均判复验失败。若 0 号机再次事故，先保存事故前位姿、控制源、安全状态和接触证据，再单独设计下一轮修复。
