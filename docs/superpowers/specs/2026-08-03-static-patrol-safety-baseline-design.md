# 固定巡逻静态安全基线设计

## 背景与根因

真实六机运行中出现两个可重复观察的现象：部分飞机在完成 3 米起飞后继续升到约 4.5 至 5 米，1、2、3 号机还会进入相同的 `y=0` 中央通道。

起飞节点本身的目标高度仍是 3 米，并会在每架飞机分别到高后停止该机爬升。继续升高来自任务接管后的巡逻航点：当前 `mission_down.json` 分别使用 3.5、4.0、4.5 和 5.0 米。路线重叠也不是任务分配串线；任务启动器按 `vehicle_id` 读取对应条目，但任务文件本身让 1、2、3 号机共享了从 `x=-8` 到 `x=100` 的中央通道。

这些中央绕行点是此前为避开加油站等高于比赛限高的建筑而加入的。现有测试能够阻止航点超过 6 米和航段穿过已登记静态障碍，却没有检查起点到首航点、不同无人机的航线交叉、共线重叠或最小间距。因此当前任务可以通过自动测试，同时仍表现出明显的集群路线冲突。

仓库还存在两份内容不同的 `mission_down.json`。ROS Launch 实际读取 `src/mix_nav/task_manager/launch/mission_down.json`，而根目录 `waypoint/mission_down.json` 容易被误认为运行时来源。

## 目标与边界

本次建立 EGO-Planner-Swarm 接入前的固定巡逻静态安全基线：

- 六架飞机使用 `3 列 x 2 行`互斥责任区；
- 起飞区外的任意两条固定任务路线不交叉、不共线，中心线最近距离至少 5 米；
- 起飞目标保持 3.0 米，固定巡逻目标统一为 3.5 米，最终速度安全过滤的高度上限收紧为 4.0 米；
- 每架飞机只进入责任区一次，随后只在本区域内闭环循环；
- 人物跟踪打断进入或巡逻后，能够返回中断点并继续原阶段；
- 当前基线未来可直接作为 EGO 固定分区的初始条带和失效降级任务。

本次只修改队伍自有的 `task_manager`、任务 JSON、`safety_filter` 配置、测试和文档。不得修改 PX4、XTDrone、Gazebo、EGO-Planner-Swarm、第三方插件或官方无人机模型。

本次不实现 EGO 动态规划、动态机间避碰、未知地图前沿分配或跟踪状态下的跨机避碰。5 米约束只约束固定任务中心线；真实控制误差仍必须通过 Gazebo 全航程回归观察。

## 方案比较与选择

比较过三种总体布局：

1. `3 列 x 2 行`责任区：每机只负责一个局部区域，远区通过南北外围通道进入；覆盖职责清晰，最适合未来沿用为 EGO 固定分区。
2. 六条水平搜索带：规则简单，但南侧建筑会切断多条搜索带，重新形成公共绕行瓶颈。
3. 保留全场大环线并拆分专用通道：改动较小，但长距离重复覆盖、转弯多，也难以转成 EGO 责任区。

选择方案 1。它需要重新设计任务数据结构和航点，但能从根本上消除多机反复走同一条全场路线的问题。

## 责任区与高度

责任区分配固定为：

| 无人机 | 责任区 | 进入方向 |
| --- | --- | --- |
| `typhoon_h480_0` | 西南 | 从起飞区向西南进入近区 |
| `typhoon_h480_1` | 南中 | 从起飞区向东南进入中区 |
| `typhoon_h480_2` | 东南 | 使用南侧外围通道进入远区 |
| `typhoon_h480_3` | 西北 | 从起飞区向西北进入近区 |
| `typhoon_h480_4` | 北中 | 从起飞区向东北进入中区 |
| `typhoon_h480_5` | 东北 | 使用北侧外围通道进入远区 |

六机出生点位于 `x=-17/-14`、`y=-3/0/3` 的紧凑网格，最近间距约 3 米，因此 5 米路线隔离从离开起飞区后开始执行。起飞区定义为能够完整包住六个出生点和初始发散段的测试常量；只有位于该区域内的路线片段可以豁免跨机 5 米检查，豁免不得延伸到搜索区或长距离通道。

固定任务的 `entry_waypoints` 和循环 `waypoints` 全部使用 3.5 米。起飞节点继续到 3.0 米，交权后只进行约 0.5 米的平缓爬升。`safety_filter` 的 `max_altitude` 改为 4.0 米；达到边界时现有安全策略禁止继续向上速度，不改变最低高度、水平速度或加速度限制。

相邻责任区的循环方向采用棋盘式交错顺逆时针，使相邻边界上的运动方向尽量一致，避免形成相向飞行。精确航点不靠人工目测验收，必须同时满足下文的建筑净空、闭环、交叉和最小距离检查后才能写入任务文件。

## 任务文件结构

任务条目增加可选的 `entry_waypoints`：

```json
{
  "vehicle_id": "typhoon_h480_0",
  "entry_waypoints": [
    {"x": -25.0, "y": -10.0, "z": 3.5}
  ],
  "waypoints": [
    {"x": -45.0, "y": -10.0, "z": 3.5},
    {"x": -45.0, "y": -40.0, "z": 3.5},
    {"x": -10.0, "y": -40.0, "z": 3.5}
  ]
}
```

上例只说明字段语义，不是最终飞行坐标。`entry_waypoints` 从出生点开始只执行一次；`waypoints` 的最后一个点到第一个点构成隐式闭合航段并持续循环，任务文件不重复写首点。

兼容规则：

- 没有 `entry_waypoints` 的旧任务直接进入现有循环巡逻行为；
- 存在该字段时必须是非空数组；
- 固定安全基线中的六个任务均必须提供进入路线和至少三个循环航点；
- `vehicle_id` 必须非空且在同一文件中唯一；
- 航点必须包含有限数值 `x/y/z`，不接受缺字段、NaN 或无穷值；
- 任一任务条目无效时，启动器在创建飞行线程前整体失败，不能让部分飞机带着不完整任务起飞。

ROS 包内的 `src/mix_nav/task_manager/launch/mission_down.json` 继续作为唯一运行时权威文件。根目录 `waypoint/mission_down.json` 改为指向该文件的相对符号链接，使既有可见入口仍可使用，但不再维护第二份内容。测试必须验证链接能够解析到权威文件。

## 任务状态机

任务管理器增加明确的进入阶段：

```text
IDLE -> ENTERING -> PATROLLING
             \          \
              -> PAUSED -> RESUMING -> 暂停前的活动阶段
```

行为约束：

1. 有进入路线的任务从 `ENTERING` 开始，使用独立的进入航点索引；全部到达后将索引封存并转为 `PATROLLING`。
2. `PATROLLING` 只循环区域内航点，不重新执行进入路线，也不返回起飞区。
3. 没有进入路线的兼容任务直接进入 `PATROLLING`。
4. 收到 `PAUSE` 时记录暂停前的活动阶段、当前航点索引和中断位置，再沿用现有路径栈记录跟踪期间的运动。
5. 收到 `RESUME` 后沿现有路径栈返回中断点；若暂停前为 `ENTERING`，继续剩余进入航点；若为 `PATROLLING`，继续当前区域循环。
6. 暂停和恢复不得把进入索引重置为零，也不得把已经完成的进入路线重新开放。
7. 现有目标锁定、三路 MUX、后置安全过滤及最终发布者所有权保持不变。

## 几何安全检查

航线测试使用二维线段几何计算，结构化读取 JSON，不以源码字符串作为行为证据。

### 静态障碍净空

测试的完整任务几何包括：

- 已知出生点到第一个进入航点；
- 相邻进入航点；
- 最后一个进入航点到第一个循环航点；
- 相邻循环航点；
- 最后一个循环航点到第一个循环航点的闭合段。

每一段继续对已登记建筑和路灯保留 2 米水平余量。障碍高度高于固定巡逻高度时不得从上方跨越。测试必须补上当前遗漏的“出生点到首航点”和“循环末点到首点”。

### 跨机隔离

对不同无人机的以下组合全部计算线段最近距离：

- 进入路线与进入路线；
- 进入路线与循环路线；
- 循环路线与循环路线。

线段相交或共线重叠时距离为零，直接失败。将位于起飞区内的线段部分裁掉后，其余几何的最近距离必须至少为 5 米。测试失败信息必须列出两架飞机、双方航段编号、计算距离和端点，便于调整单个航点。

5 米是固定路线中心线要求，不替代真实动力学验收。由于导航器存在 3 米到点容差、转弯和速度连续性，最终还要在 Gazebo 中记录实际轨迹、机间最近距离、最高高度和接触事件。

## 异常处理

- JSON 无法解析或结构无效：任务启动器整体非零退出，不创建任何 `MissionManager` 线程。
- 某个请求的 `vehicle_id` 不存在：固定六机任务视为整体错误，不再仅警告并跳过；避免五机飞行掩盖任务缺失。
- 进入阶段被人物跟踪打断：保存 `ENTERING`，返回中断点后继续剩余进入航点。
- 巡逻阶段被人物跟踪打断：保存 `PATROLLING`，返回中断点后继续当前循环索引。
- 任务路线静态检查失败：不得启动真实仿真验收，不通过提高高度或修改官方世界绕过。
- 实际飞行出现路线偏离、机间过近、建筑接触或高度达到 4 米边界：保留日志和轨迹证据，回到航点设计或队伍控制参数排查；不得修改 PX4、XTDrone、Gazebo 或官方模型来匹配任务。

## 测试与验收

实现严格按测试先行：先用当前 `mission_down.json` 证明跨机重叠检查失败，再修改任务结构和航点使其通过。

自动测试至少覆盖：

1. 当前中央共线段被跨机几何测试检出；
2. 起点到首航点和循环闭合段参与障碍检查；
3. 相交、共线重叠、平行不足 5 米和恰好 5 米的边界行为；
4. 起飞区豁免只裁掉区域内部分，不豁免离开起飞区后的长航段；
5. 六机任务的编号、进入路线、循环点数、高度和有限数值校验；
6. 无效任务整体失败，不产生部分任务线程；
7. 无进入路线的旧任务保持兼容；
8. 进入路线只执行一次，循环时不返回起飞区；
9. `ENTERING` 和 `PATROLLING` 分别被暂停后能够恢复原阶段和原索引；
10. `waypoint/mission_down.json` 解析到唯一权威任务文件；
11. `safety_filter` 在 4.0 米处阻止继续上升，并保持其他限制不变；
12. 最终 XTDrone 速度话题仍只有对应 `safety_filter` 一个队伍发布者。

自动化通过后执行完整 `competition-clean` verifier。真实六机验收必须确认：

- 六机均在 3 米完成起飞，交权后巡逻目标为 3.5 米；
- 实际最高高度不持续越过 4.0 米，任何触发高度边界的情况均记录并分析；
- 每架只执行一次进入路线，之后留在本责任区闭环巡逻；
- 固定巡逻期间没有共用航段、路线交叉、无人机接触或静态障碍接触；
- 跟踪分别在进入阶段和巡逻阶段发生时，返回后都能继续正确阶段；
- smoke、最终发布者唯一性和起飞门控继续通过；
- PX4、XTDrone、Gazebo、EGO、第三方插件及官方模型在运行前后保持不变；
- Ctrl-C 正常返回，项目进程和本次临时目录无残留。

## 后续与 EGO 的关系

本设计不接入 EGO-Planner-Swarm。后续 EGO 阶段将六个责任区转换为固定分区约束，将区域内循环点转换为初始条带或短距离探索目标；EGO 负责局部动态绕障和多机轨迹避碰。静态任务继续保留为 EGO 不可用时的降级路线。

EGO adapter 只能替换现有 navigator 输入发布者，不能增加第四路 MUX，也不能直接发布 XTDrone 最终速度话题。当前安全基线不会改变这一控制边界。
