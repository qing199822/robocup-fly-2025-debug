# 未知地图下的多无人机自主搜索方案调研

更新日期：2026-08-02

本文是一份方案讨论和技术选型记录，不是已经完成的功能说明，也不代表相关开源项目已经接入当前仓库。本文不要求修改 PX4、XTDrone、Gazebo 或无人机基础模型；未来若实施，只应在队伍自己的 ROS 包、Launch 和允许的传感器配置范围内完成。

## 1. 结论摘要

2025 年赛事规则描述的实际问题是：

- 城市边界和飞行任务范围已知；
- 建筑物、灯杆等模型的位置会在每次尝试前随机生成，因此障碍地图未知；
- 比赛过程有卫星导航信号，因此不需要把 VIO/SLAM 当作主定位来源；
- 六架无人机需要在 10 分钟内搜索六名会移动、逃跑和瞬移的人物；
- 搜索时间、传感器造价和碰撞次数共同影响成绩。

因此，系统的首要问题不是“在没有定位的情况下同时定位与建图”，而是：

1. 将六架无人机的位置统一到同一个全局坐标系；
2. 根据深度或激光数据在线建立障碍地图；
3. 将未知区域高效地分配给六架无人机；
4. 在地图持续更新时进行局部避障和重规划；
5. 识别人后中断探索并跟踪，完成后重新加入搜索。

当前最推荐的总体路线是：

```text
GPS/MAVROS 全局定位
  + 每机 Realsense 局部三维占据地图
  + 中央 2.5D 融合地图和覆盖记录
  + 六区域条带搜索
  + 前沿探索补漏
  + EGO-Planner-Swarm 局部规划与机间避碰
  + 现有 YOLO、目标锁和 MUX 跟踪链路
```

这个组合优先保证 10 分钟内的覆盖效率和可调试性，同时保留进一步替换为 FUEL 或 RACER 风格探索器的接口。

## 2. 赛事规则依据

本地规则文件：

- [2025 多旋翼无人机集群协同搜索仿真赛事规则](../../16.2赛事规则.无人机挑战赛-多旋翼无人机集群协同搜索仿真.2025%20中国机器人大赛暨RoboCup机器人世界杯中国赛（复件）.pdf)

规则中的关键约束如下：

| 项目 | 规则内容 | 对方案的影响 |
| --- | --- | --- |
| 场地 | 约 200m x 100m 仿真城市 | 全局边界已知，可以预先定义探索范围 |
| 地图 | 建筑物、灯杆等位置每次由脚本随机生成 | 不能使用固定航点绕障，必须在线感知和重规划 |
| 定位 | 比赛过程均有卫星导航信号 | 优先使用 GPS/MAVROS，不必承担完整 SLAM 定位风险 |
| 无人机 | 固定 6 架，飞行高度低于 6m | 适合固定搜索高度和 2.5D 全局规划 |
| 人物 | 6 人，平时约 1m/s，逃跑约 2m/s，可能瞬移 | 人物必须进入动态目标层，不能固化进静态障碍地图 |
| 时间 | 每次最长 10 分钟，无人工干预 | 启动、建图、搜索、故障恢复必须全部自动完成 |
| 通信 | 无通信距离限制 | 可以采用中央地图和中央任务分配，不必强行完全去中心化 |
| 计分 | 时间、传感器造价、碰撞次数共同计分 | 不能只追求算法复杂度；需要比较成本和稳定性 |
| 传感器 | 单目、双目、测距仪、二维/三维雷达和云台 | 可选择视觉或激光路线，但参数必须保持 XTDrone 原版 |

规则列出的传感器价格：

| 传感器 | 单价 |
| --- | ---: |
| 单目相机 | 500 元 |
| 双目相机 | 1000 元 |
| 激光测距仪 | 200 元 |
| 二维激光雷达 | 1000 元 |
| 三维激光雷达 | 2000 元 |
| 云台 | 200 元 |

注意：当前使用的 Realsense 在最终计分中按哪一类传感器计价，应向当年裁判确认，不能只根据设备名称自行推断。

## 3. 当前项目与未知地图需求之间的差距

当前项目已经具备：

- 六机 PX4、MAVROS 和 XTDrone 通信；
- 已知起点偏移下的统一坐标处理；
- JSON 预设航点任务；
- 简单航点导航；
- YOLO 人物分类识别；
- 深度坐标解算；
- 目标唯一锁定；
- 跟踪状态机、MUX 控制权切换和任务恢复。

当前项目尚不具备：

- 从 Realsense 或激光数据持续建立障碍占据地图；
- 六机地图融合和地图时效管理；
- 已搜索区域覆盖率记录；
- 未知区域的前沿提取；
- 根据距离、风险和负载自动分配探索目标；
- 基于障碍地图的实时局部轨迹重规划；
- 对移动人物产生的临时障碍进行衰减或语义剔除。

现有固定航点仍可作为降级策略，但不能作为随机障碍地图中的主导航方案。

## 4. 推荐的通用系统分层

无论最终选择哪种开源规划器，建议保持以下模块边界。

### 4.1 定位层

职责：把六架无人机的位置放入同一个全局 ENU 坐标系。

首选输入：

- MAVROS 全局 GPS；
- PX4 本地位置；
- 每架无人机的已知起飞点或可靠的 GPS 原点转换。

需要在正式实现前确认：

- 六架 PX4 是否共享同一 GPS 原点；
- `/mavros/global_position/*` 是否在正式赛场镜像中稳定发布；
- 若 PX4 没有初始化全局原点，是否允许使用已知起飞点偏移完成对齐。

不建议同时把 GPS、硬编码偏移和 VIO 都作为全局真值来源，否则容易形成坐标闭环或重复补偿。

### 4.2 感知与局部地图层

每架无人机根据自己的深度图或点云构建有限半径的局部三维占据地图。

建议参数方向：

- 地图只覆盖无人机附近，避免六机都维护完整高分辨率城市地图；
- 为机体尺寸、控制误差和通信延迟增加安全膨胀；
- 未观察区域保持 unknown，不能默认可通行；
- 对动态障碍设置时间衰减；
- YOLO 检测框对应的点云不要写入永久静态地图。

### 4.3 全局融合与覆盖层

中央节点维护低分辨率 2.5D 地图：

- 地面网格是否已观察；
- 该网格在搜索高度上是否可通行；
- 最近观察时间；
- 当前负责的无人机；
- 是否包含尚未完成的前沿。

2.5D 地图负责大范围搜索分工；每机局部 3D 地图负责屋檐、灯杆、墙面和机间避碰。这样比让中央节点融合六份完整 ESDF 更容易在 10 分钟任务中保持实时性。

### 4.4 探索与任务分配层

建议采用两个阶段：

1. 快速覆盖：把 200m x 100m 范围分成六个区域，每架执行条带式或回字形搜索；
2. 前沿补漏：根据在线地图识别仍未观察的边界区域，重新分配给空闲无人机。

任务分配代价可以包含：

```text
总代价 = 到达距离
       + 障碍风险
       + 与其他无人机的冲突风险
       + 当前任务负载
       - 预计新增覆盖面积
```

中央协调适合本赛事，因为通信距离不受限制，也便于与当前目标锁服务和任务管理器结合。

### 4.5 局部规划和控制层

局部规划器接收一个短距离探索目标，结合局部三维地图生成安全轨迹。它不应该直接绕过现有 MUX 发布最终控制命令。

正确的控制边界应保持为：

```text
探索目标/轨迹
  -> 队伍导航适配节点
  -> pose_cmd_mux 的任务输入
  -> XTDrone 最终控制话题

跟踪节点
  -> pose_cmd_mux 的 external 输入
  -> XTDrone 最终控制话题
```

### 4.6 人物跟踪与任务恢复层

发现人物后的建议流程：

1. 申请目标唯一锁；
2. 暂停该无人机的探索任务；
3. MUX 切换到视觉跟踪控制；
4. 其他无人机继续搜索，不能全部围向同一人物；
5. 人物消失或任务完成后，释放目标锁；
6. 从中央协调器领取最近的未完成前沿，而不是盲目返回旧的固定航点。

现有路径栈可以保留为通信或地图失效时的保守返航手段。

## 5. 方案 A：轻量混合探索加 EGO-Planner-Swarm（推荐）

### 5.1 组成

- 当前 Realsense 深度和 RGB；
- GPS/MAVROS 统一位置；
- 队伍自有中央 2.5D 地图与覆盖管理；
- 队伍自有六区域条带搜索和前沿补漏；
- EGO-Planner-Swarm 负责局部三维规划和多机轨迹避碰；
- 当前 YOLO、目标锁、tracking 和 MUX 链路保持不变。

### 5.2 优点

- XTDrone 官方已有 EGO-Planner-Swarm 集成教程；
- EGO-Planner-Swarm README 明确支持 Ubuntu 20.04 和 ROS1；
- 与当前六机和 Realsense 组合接近；
- 搜索策略由队伍自己实现，便于满足比赛查重要求；
- 可以先完成条带覆盖，再逐步增加前沿补漏；
- 出现问题时容易判断是地图、分配、局部规划还是控制接口故障。

### 5.3 缺点

- EGO-Planner-Swarm 不是完整探索器，不会自动决定下一块未知区域；
- 官方仿真默认可使用 fake drone，接入时必须确保使用真实 PX4/XTDrone 控制链；
- 需要明确 odometry、深度、点云、轨迹和 MUX 之间的接口适配；
- GPL-3.0 许可证和赛事源码提交要求需要单独审查。

### 5.4 适用判断

这是当前项目最稳妥的主线。它复用成熟的局部规划和机间避碰，但把比赛真正考核的覆盖策略、目标分工和任务恢复保留在队伍包中。

## 6. 方案 B：FUEL 单机探索器加中央六机分配

### 6.1 组成

- 每架运行一套 FUEL 局部地图和前沿探索；
- 中央协调器为每架分配互不重叠的空间边界或候选前沿；
- 当前跟踪节点接管时，暂停对应 FUEL 实例；
- 完成跟踪后重新加入前沿竞价。

### 6.2 优点

- FUEL 官方 README 明确测试 Ubuntu 20.04/ROS Noetic；
- 自带增量前沿结构、分层规划和最小时间轨迹；
- 比单纯条带搜索更能主动补齐建筑遮挡后的未知区域；
- 开源仿真示例完整，适合先在独立工作区验证。

### 6.3 缺点

- FUEL 主体是单机探索框架；六份实例可能重复维护地图和前沿；
- 与当前任务管理、EGO、导航器和 MUX 的职责可能重叠；
- 直接同时使用 FUEL 完整规划器和 EGO 会造成双规划器竞争；
- 六机同时运行的 CPU 和内存成本需要真实测量；
- GPL-3.0，且算法核心直接复用可能触发赛事查重解释成本。

### 6.4 适用判断

适合作为第二路线或算法参考。若采用，应该明确选择“FUEL 完整负责单机地图和轨迹”或“只借鉴其前沿管理思想”，不应与 EGO 重复堆叠完整规划链路。

## 7. 方案 C：RACER 风格的完全分布式多机探索

### 7.1 组成

- 每架无人机维护自己的局部地图和前沿；
- 无人机之间交换前沿、轨迹和工作负载；
- 使用分布式任务分配平衡六机覆盖；
- 不依赖中央协调器持续在线。

### 7.2 优点

- RACER 的目标与本比赛最接近：多无人机、未知环境、协同探索；
- 官方 README 声明测试 Ubuntu 20.04/ROS Noetic；
- 对通信异步和不稳定具有设计上的鲁棒性；
- 理论上能减少重复覆盖并提高探索效率。

### 7.3 缺点

- 系统复杂度最高，调试面包括地图一致性、前沿同步、任务冲突和轨迹冲突；
- 比赛通信距离无限，完全去中心化带来的收益未必抵得过实现风险；
- 当前 RACER 仓库根目录未发现许可证文件，不能因为源码公开就推断允许复制、修改或重新发布；
- 赛事明确对自主建图、运动规划和协同逻辑查重，直接复制核心模块风险很高；
- 与当前中央目标锁和任务管理架构差异较大。

### 7.4 适用判断

建议阅读论文和数据流，借鉴“前沿竞价、负载均衡、轨迹交换”的思想，由队伍重新实现清晰、较小的协调模块。在许可证没有明确前，不建议把 RACER 源码直接并入比赛仓库。

## 8. 方案 D：二维激光雷达加固定高度 2D/2.5D 搜索

### 8.1 组成

- 六架无人机固定在若干安全搜索高度；
- 每架使用二维激光雷达构建水平占据栅格；
- 中央融合栅格并分配条带或前沿；
- 视觉相机只负责人物识别和跟踪。

### 8.2 优点

- 墙面和灯杆距离测量稳定；
- 2D 栅格、A* 和前沿算法成熟，计算量远低于完整三维 ESDF；
- 地图容易融合和可视化；
- 故障定位比复杂三维规划简单。

### 8.3 缺点

- 需要额外支付二维雷达成本；
- 单个水平扫描面不能表达屋檐、倾斜物体和不同高度障碍；
- 飞行高度变化时旧的二维地图可能失效；
- 仍需要相机完成目标识别，因此不是用雷达完全替代视觉。

### 8.4 适用判断

如果真实随机地图主要由贯穿飞行高度的建筑和灯杆组成，并且队伍优先追求稳定避障，这条路线值得保留。正式选择前需要用裁判随机地图统计不同高度下的障碍结构。

## 9. 方案 E：三维激光雷达加完整体素探索

### 9.1 组成

- 三维激光点云；
- OctoMap、Voxblox 或 FIESTA 构建三维占据/ESDF；
- FUEL、Fast-Planner 或自有前沿探索产生目标和轨迹；
- 中央或分布式地图融合。

### 9.2 优点

- 三维障碍感知范围和几何表达最强；
- 不依赖纹理和光照；
- 适合复杂屋檐、立体通道和高度变化。

### 9.3 缺点

- 三维激光雷达价格最高；
- 六路点云、体素融合和规划计算量大；
- 地图分辨率、更新频率和内存需要精细平衡；
- 对当前只验证过 Realsense 的项目改动较大；
- 在 6 米限高、室外城市搜索中，性能收益可能不足以抵消成本。

### 9.4 适用判断

适合追求最高避障能力或随机地图存在显著三维结构的情况，不建议作为第一版方案。

## 10. 方案 F：VIO/SLAM 无 GPS 备用路线

虽然 2025 规则保证卫星导航信号，仍可保留无 GPS 的理论备用方案：

```text
双目/深度相机
  -> VINS-Fusion 或其他 VIO
  -> RTAB-Map/体素地图
  -> 探索器
  -> 局部规划器
```

### 优点

- 不依赖 GPS；
- 能处理未来规则改变或室内扩展场景；
- XTDrone 文档已有视觉 SLAM 和 VINS-Fusion 示例。

### 缺点

- 六机 VIO、闭环和稠密建图的计算量很高；
- 各机地图坐标对齐困难；
- 漂移会污染地图融合、目标坐标和轨迹避碰；
- 当前规则下增加了不必要的主要故障源。

### 适用判断

不作为 2025 规则主线。只有在正式环境确认 MAVROS GPS/全局坐标不可用时，才应重新评估。

## 11. 地图技术选型

### 11.1 OctoMap

定位：通用概率三维占据地图。

适合：

- 融合点云；
- 表示 free、occupied 和 unknown；
- 输出全局地图和可视化。

不足：

- 不负责探索目标和轨迹规划；
- 六机高分辨率全局更新可能产生通信和 CPU 压力；
- 动态人物需要额外的衰减或语义过滤。

### 11.2 Voxblox

定位：TSDF/ESDF 体素地图，BSD-3-Clause。

适合：

- 需要连续障碍距离和梯度的优化型规划器；
- CPU 多线程局部地图。

不足：

- 本身不提供完整的多机探索策略；
- 与 EGO/Fast-Planner 自带地图同时使用可能重复计算。

### 11.3 FIESTA

定位：快速增量 ESDF，MIT。

特点：

- 支持深度、点云和激光输入；
- 设计中区分障碍插入和删除；
- 对需要清除动态障碍残影的场景有参考价值。

不足：

- 项目较老；
- 仍需另配探索和轨迹规划器；
- 接入 Noetic 和当前消息接口需要单独验证。

### 11.4 Fast-Planner 内置地图

定位：深度图/点云加 odometry，在线构建概率体素和 ESDF。

优点：地图和规划器接口一致，官方明确测试 Noetic。

不足：若只使用 EGO-Planner-Swarm，则没有必要再引入一套完整 Fast-Planner。

### 11.5 RTAB-Map

定位：RGB-D、双目或激光 SLAM 与图优化系统，BSD-3-Clause。

优点：ROS Noetic 二进制和文档成熟，适合需要闭环定位和稠密重建的场景。

不足：本比赛已有 GPS，六机同时运行完整图优化可能浪费算力并引入地图坐标冲突。

## 12. 探索策略选型

### 12.1 固定条带覆盖

优点：确定、快速、容易预测 10 分钟内的覆盖率。

缺点：建筑遮挡会形成未观察死角，固定航线可能频繁被局部规划器绕开。

用途：第一阶段快速扫图和降级策略。

### 12.2 纯前沿探索

优点：直接面向未知区域，理论覆盖更完整。

缺点：六机容易争抢相同前沿；候选前沿抖动会造成反复改目标；大场地早期效率可能低于条带搜索。

用途：条带搜索后的补漏，或 FUEL/RACER 路线的主策略。

### 12.3 条带加前沿混合

优点：前期有确定覆盖速度，后期能补齐遮挡区域；便于设置时间预算。

建议时间逻辑示例：

- 前 60% 时间执行分区条带搜索；
- 中间 30% 时间按前沿和目标发现情况动态补漏；
- 最后 10% 时间停止远距离新任务，处理已发现目标并进入保守收尾。

具体比例必须根据真实仿真回归调整，不能直接视为最终参数。

### 12.4 信息增益探索

为每个候选视点估计可新增观察面积，再除以到达成本和风险。

优点：比最近前沿更有效率。

缺点：需要视场模拟和更多计算，参数不当会偏向远处大前沿。

用途：在条带加前沿方案稳定后升级。

## 13. 六机任务分配选择

### 中央分配

中央节点掌握全部无人机、目标锁、覆盖率和前沿。

优点：实现清晰、避免重复、符合无限通信距离规则、容易调试。

缺点：中央节点故障会影响全部无人机。

这是当前项目的推荐方式。

### 分布式竞价

每架无人机计算自己到前沿的代价并交换报价。

优点：没有单点故障，接近 RACER 架构。

缺点：一致性、超时和冲突处理复杂。

适合作为后续升级，不适合作为第一版。

### 固定分区

启动时把地图切成六块，不再动态调整。

优点：最简单，几乎不会重复搜索。

缺点：某一区域障碍密集或无人机跟踪人物后，工作负载会严重不均衡。

适合作为中央协调器失效时的降级模式。

## 14. 动态人物与动态障碍处理

比赛人物会移动和瞬移，地图层需要特别处理：

1. YOLO 检测到人物后，将检测框关联的深度点标记为动态语义目标；
2. 这些点可以进入短期避障层，但不能写入永久建筑地图；
3. 动态占据在短时间未重新观测后自动清除；
4. 人物瞬移后立即释放旧空间中的动态占据；
5. 人物轨迹预测只服务跟踪，不应修改 PX4 或 Gazebo 物理模型；
6. 局部规划器必须区分“其他无人机轨迹”和“未知移动人物”。

EGO-Planner-Swarm 的多机避碰主要解决无人机之间的轨迹冲突，不能直接等同于对任意动态人物的速度预测。第一版可使用短期占据和保守减速；后续再增加匀速预测。

## 15. 安全与降级策略

系统至少需要以下运行状态：

```text
TAKEOFF
MAPPING_SEARCH
TRACKING
REJOIN_SEARCH
HOLD
RETURN_OR_FINISH
```

建议降级条件：

- 深度数据超时：停止前进并悬停，不把 unknown 当 free；
- 局部规划连续失败：退回最近安全点，再向中央申请新目标；
- 全局地图不同步：继续执行本机局部安全规划和固定分区；
- 中央协调器失联：保持原分区，避免所有无人机停飞；
- GPS/公共坐标异常：禁止融合地图和跨机轨迹，进入悬停或本地模式；
- 跟踪目标丢失：按现有缓冲机制尝试恢复，超时后回到安全搜索任务；
- 控制 MUX 切换失败：不得同时向最终 XTDrone 控制话题发布多个命令源。

## 17. 建议的验证顺序

以下是未来若决定实施时的验证顺序，不代表现在开始修改代码。

### 阶段 1：单机地图

- 静止无人机能把墙、房屋和灯杆写入地图；
- free、occupied、unknown 区分正确；
- 人物移动后不会留下永久障碍；
- 地图坐标与 MAVROS/世界坐标一致。

### 阶段 2：单机局部规划

- 向障碍物后的目标点飞行时能够绕行；
- 深度中断时悬停；
- 重规划不会造成速度突变；
- 飞行高度始终低于 6 米并保留安全余量。

### 阶段 3：六机分区覆盖

- 六机初始区域不重复；
- 地图融合不会因坐标原点不同而错位；
- 无人机之间保持安全距离；
- 某架跟踪人物时，其他五架继续搜索。

### 阶段 4：前沿补漏

- 建筑遮挡后的区域会被识别为未覆盖；
- 同一前沿不会长期分配给多架无人机；
- 前沿消失或不可达时能够及时换目标；
- 覆盖率随时间单调增长，不发生大面积误清除。

### 阶段 5：完整随机地图回归

- 使用多组裁判式随机地图；
- 每组运行完整 10 分钟或提前完成；
- 记录搜索人数、完成时间、碰撞数、重规划次数、目标丢失次数和 CPU/GPU 峰值；
- 测试正常退出后没有 PX4、Gazebo、YOLO 或通信进程残留；
- 验证 PX4、XTDrone、Gazebo 官方目录哈希不变。

## 18. 方案决策矩阵

评分为相对判断，5 分最好；“成本”得分越高表示传感器和集成成本越低。

| 方案 | 完赛稳定性 | 探索效率上限 | 集成难度 | 算力压力 | 成本 | 许可证/查重风险 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A. Realsense + 混合探索 + EGO | 5 | 4 | 3 | 3 | 5 | 中 |
| B. FUEL + 中央六机分配 | 3 | 4 | 2 | 2 | 5 | 中高 |
| C. RACER 风格分布式探索 | 2 | 5 | 1 | 2 | 5 | 高 |
| D. 二维雷达 + 2.5D 搜索 | 4 | 3 | 4 | 4 | 2 | 低 |
| E. 三维雷达 + 完整体素探索 | 4 | 5 | 2 | 1 | 1 | 取决于规划器 |
| F. VIO/SLAM 无 GPS | 2 | 3 | 1 | 1 | 4 | 取决于 SLAM 项目 |

这里的分数是基于当前项目状态的工程判断，不是实测结果。正式决策应以相同随机地图上的重复试验数据为准。

## 19. 最终建议

建议按照以下优先级研究：

1. 主线：方案 A，使用现有 Realsense、中央 2.5D 覆盖、条带加前沿、EGO 局部规划；
2. 算法参考：阅读 FUEL 的前沿信息结构和 RACER 的多机分配，但队伍自行实现协调逻辑；
3. 备选：如果 Realsense 对灯杆和建筑避障不稳定，再评估二维激光雷达方案；
4. 暂缓：三维雷达和完整 VIO/SLAM，除非真实随机地图或正式环境证明有必要。

第一版的成功标准不应是“用了最复杂的算法”，而应是：

- 不依赖固定障碍坐标；
- 六机不会重复挤在同一区域；
- 能在新障碍前停止或绕行；
- 发现人物后仍能稳定跟踪；
- 跟踪结束后其余搜索任务不丢失；
- 10 分钟内覆盖率和发现人数稳定；
- 不修改 PX4、XTDrone、Gazebo 和官方模型核心源码。
